# Cursor + 1С: Предприятие — настройка контекста через MCP

Этот репозиторий настроен так, чтобы **чат и агент Cursor (в т.ч. Cloud Agent)
видели метаданные и код вашей базы 1С** и могли вносить доработки прямо в
исходники конфигурации.

> Коротко: вы выгружаете конфигурацию 1С «в файлы» в папку `1c-config/src/`,
> Cursor поднимает MCP-сервер файловой системы поверх этой папки, агент читает
> метаданные и модули и редактирует их напрямую. Вам останется загрузить
> конфигурацию обратно в базу.

---

## 1. Что такое MCP и зачем он здесь

**MCP (Model Context Protocol)** — открытый протокол, через который Cursor
подключает внешние инструменты/источники данных к LLM. Каждый MCP-сервер —
это маленький процесс (npx/uvx/python/exe), который умеет, например,
читать файлы, ходить в Git, дергать API.

Cursor читает конфигурацию MCP из файла `.cursor/mcp.json` в корне проекта
(или глобально из `~/.cursor/mcp.json`). После этого в чате и в агенте
появляются новые инструменты, которые модель сама вызывает по необходимости.

В этом репозитории уже настроены три сервера — см. `.cursor/mcp.json`:

| Сервер | Что делает | Зачем для 1С |
|---|---|---|
| `filesystem-1c` | Доступ к файлам внутри `1c-config/` | Чтение метаданных XML и модулей `.bsl` |
| `git` | История, ветки, diff | Видеть, что вы поменяли в конфигурации |
| `sequential-thinking` | Структурированное рассуждение | Помогает модели планировать доработки по шагам |

> Важно: Cursor и так умеет читать файлы открытого проекта. MCP-сервер
> `filesystem-1c` нужен в первую очередь для **чата** (где обычный
> file-tool ограничен) и для надёжного доступа к большим выгрузкам — в
> агентном режиме файлы из проекта читаются и без него.

## 2. Куда класть выгрузку базы

```
<repo>/
├── .cursor/
│   ├── mcp.json          ← конфиг MCP-серверов
│   └── rules/1c.mdc      ← правила, которые агент применяет всегда
├── 1c-config/
│   ├── src/              ← СЮДА — выгрузка конфигурации в файлы
│   └── ext/              ← внешние обработки/отчёты, расширения
└── README.md
```

Подробная инструкция по выгрузке (Конфигуратор / EDT / внешние объекты) — в
[`1c-config/README.md`](1c-config/README.md).

Если коротко (Конфигуратор):

1. Открыть базу в Конфигураторе.
2. **Конфигурация → Выгрузить конфигурацию в файлы…** → выбрать
   `…/1c-config/src/`.
3. Закоммитить результат: `git add 1c-config/src && git commit -m "config dump"`.

После доработок агентом — **Конфигурация → Загрузить конфигурацию из файлов…**
из той же папки, обновить конфигурацию БД (`F7`) и принять изменения.

## 3. Как пользоваться чатом и агентом

### В Cursor Desktop

1. Установить Node.js 18+ (для `npx`) и, желательно, [`uv`](https://docs.astral.sh/uv/)
   (для `uvx`) — нужны MCP-серверам.
2. Открыть этот репозиторий в Cursor.
3. **Settings → MCP → Enable**. Проверить, что в списке появились
   `filesystem-1c`, `git`, `sequential-thinking` со статусом «running».
4. В чате (`Ctrl/Cmd+L`) задавать вопросы по конфигурации, например:

   - «Покажи реквизиты справочника `Контрагенты` и его подчинённые объекты».
   - «Найди все вызовы `ОбщегоНазначения.ВыполнитьПривилегированныйМетод`
     в общих модулях».
   - «Добавь в документ `РеализацияТоваровУслуг` новый реквизит
     `НомерЗаявкиCRM` (Строка, 50) и выведи его на основную форму».

5. В режиме агента (`Ctrl/Cmd+I`) — те же запросы, но агент сам отредактирует
   файлы под `1c-config/src/...` и покажет diff.

### В Cloud Agents (этот чат)

Cloud-агент работает на удалённой VM — у него уже есть доступ к файлам
репозитория. Чтобы он «видел» вашу базу:

1. Выгрузите конфигурацию в `1c-config/src/`, закоммитьте и запушьте.
2. В задаче для агента опишите, что нужно сделать (например, «добавь реквизит
   и движение в регистр»). Агент создаст ветку, поправит файлы и оформит PR.
3. Локально подтянете PR, **Загрузить конфигурацию из файлов…**, обновите БД.

> MCP-серверы из `.cursor/mcp.json` подхватываются и Cloud Agent — отдельной
> настройки не требуется, но зависимости (`npx`, `uvx`) должны быть в образе.
> Если их нет — попросите выполнить онбординг окружения на
> [cursor.com/onboard](https://cursor.com/onboard).

## 4. BSL Language Server (проверка синтаксиса 1С)

[BSL Language Server](https://github.com/1c-syntax/bsl-language-server) — это
**LSP-сервер** (не MCP). Он подключается двумя способами:

### 4.1. В Cursor Desktop — подсветка ошибок прямо в редакторе

1. Установить расширение **«Language 1C (BSL)»** (`1c-syntax.language-1c-bsl`).
   Оно уже добавлено в `.vscode/extensions.json` как рекомендуемое — Cursor
   предложит его установить при открытии проекта.
2. Установить JDK 17+ (для BSL LS 0.29.x — JDK 21).
3. Открыть файл `*.bsl` из `1c-config/src/` — расширение само поднимет
   BSL LS, и в левом колодце редактора появятся диагностики.
4. Настройки в `.vscode/settings.json` уже включают русский язык диагностик и
   корректные ассоциации файлов.

После этого агент Cursor (Cmd/Ctrl+I) тоже видит ошибки и предупреждения и
может их исправлять.

### 4.2. В CI и в Cloud Agent — анализ всей конфигурации одной командой

В репозитории есть скрипт-обёртка `scripts/bsl-ls.sh`, который:

- скачивает нужную версию BSL LS (`bsl-language-server-<ver>-exec.jar`) в
  локальный кеш `.bsl-ls/`;
- запускает её в режиме `analyze` поверх `1c-config/src/` с конфигурацией
  `.bsl-language-server.json`;
- складывает отчёты в `reports/`.

Запуск:

```bash
# консольный отчёт
scripts/bsl-ls.sh

# JSON-отчёт (reports/bsl-json.json) — удобно читать агенту
scripts/bsl-ls.sh --reporter json

# SARIF-отчёт (reports/bsl-ls.sarif) — для GitHub code scanning
scripts/bsl-ls.sh --reporter sarif

# зафиксировать конкретную версию
BSL_LS_VERSION=0.29.0 scripts/bsl-ls.sh --reporter json
```

GitHub Actions workflow `.github/workflows/bsl-ls.yml` автоматически прогоняет
анализ на каждом PR, заливает SARIF в **Security → Code scanning** и кладёт
JSON отчёт как артефакт сборки.

### 4.3. Как этим пользуется агент

Агент (включая меня в Cloud Agents) перед доработками может вызвать
`scripts/bsl-ls.sh --reporter json` и прочитать `reports/bsl-json.json`,
чтобы знать о существующих ошибках/предупреждениях. После своих изменений —
повторить запуск, убедиться, что новых проблем нет, и только тогда
коммитить. Это поведение зафиксировано в `.cursor/rules/1c.mdc`.

## 5. Опциональные MCP-серверы под 1С

Существуют community-серверы, которые расширяют возможности (статический
анализ BSL, прямой запрос к ИБ через HTTP-сервисы и т.п.). Подключаются
аналогично — добавлением блока в `.cursor/mcp.json`. Примеры (не включены
по умолчанию, потому что требуют отдельной установки):

```json
{
  "mcpServers": {
    "bsl-ls": {
      "command": "java",
      "args": ["-jar", "/path/to/bsl-language-server.jar", "--mcp"]
    },
    "1c-http": {
      "command": "npx",
      "args": ["-y", "mcp-1c-http"],
      "env": {
        "ONEC_BASE_URL": "https://my-1c-server/base/hs/api",
        "ONEC_USER": "${ONEC_USER}",
        "ONEC_PASSWORD": "${ONEC_PASSWORD}"
      }
    }
  }
}
```

Если планируете прямой доступ к работающей ИБ через HTTP-сервис — учётные
данные кладите в **Cursor → Settings → Secrets** (или Cloud Agents → Secrets),
а не в `mcp.json`.

## 6. Безопасность

- Не коммитьте `.1CD`, `.dt`, дампы с реальными ПДн.
- Не храните пароли в `mcp.json`. Только переменные окружения / секреты Cursor.
- Перед публикацией репозитория на GitHub проверьте, что в выгрузке нет
  внутренних адресов, токенов и т.п.

стиле вашей конфигурации.
